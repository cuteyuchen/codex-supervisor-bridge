# P6.5 — Selectable Execution Modes

## Goal

Codex Supervisor Bridge must not force one fixed development style.

A user may choose whether ChatGPT Web:

1. edits and operates the local workspace directly;
2. works directly first and delegates bounded work to Codex when useful;
3. supervises Codex for the whole implementation.

The mode may also change during an active task without losing task memory, intent, plan history, revision safety, or Git/worktree continuity.

## Execution modes

### `DIRECT`

ChatGPT Web is the active developer.

The Supervisor Bridge exposes a constrained direct-workspace surface backed by DevSpace. Expected capabilities include:

- open/reuse workspace;
- read files;
- apply patches;
- run local commands;
- interact with long-running command sessions;
- inspect aggregated changes / review refs.

Codex is not started automatically in this mode. The user or Supervisor must explicitly switch/handoff before Codex may mutate the workspace.

### `HYBRID`

ChatGPT Web may develop directly and may delegate bounded work to Codex when the existing user policy permits it.

Typical flow:

```text
ChatGPT direct edits
  -> tests / investigation
  -> execution handoff
  -> Codex plan or implementation
  -> observe / steer / respond / interrupt
  -> handback
  -> ChatGPT direct follow-up
```

This is the preferred mode for "web first; use Codex when needed".

### `CODEX_SUPERVISED`

ChatGPT Web acts as product owner / architect / supervisor / reviewer.

All mutating implementation work is delegated to Codex through the Agent backend. ChatGPT may still inspect files, diffs, validation, checkpoints, and Git state, but does not directly mutate the workspace unless the user changes mode.

## Mode selection

Execution mode is task state, not a global installation setting.

It must be possible to:

- choose a mode when creating a task;
- change mode during a task;
- record the change in the append-only event timeline;
- include current mode in every Context Pack;
- reject stale mode changes through `expected_revision`;
- resume the same mode after ChatGPT or Bridge restart.

Suggested state:

```text
execution_mode: DIRECT | HYBRID | CODEX_SUPERVISED
active_writer: NONE | CHATGPT | CODEX
handoff_policy: MANUAL_ONLY | SUPERVISOR_ALLOWED
```

`HYBRID + SUPERVISOR_ALLOWED` means the user has already authorized ChatGPT to decide when a bounded Codex delegation is appropriate. `MANUAL_ONLY` means Codex may be used only after an explicit user instruction.

## Single-writer invariant

Direct ChatGPT editing and Codex must never mutate the same worktree concurrently by default.

A supervised task owns a write lease:

```text
NONE
  -> CHATGPT
  -> NONE
  -> CODEX
  -> NONE
  -> CHATGPT
```

Rules:

- reads and observation may remain available while Codex is active;
- direct `apply_patch` is allowed only while `active_writer=CHATGPT`;
- direct command execution is treated as potentially mutating and requires the ChatGPT write lease;
- Codex implementation starts only while `active_writer=CODEX`;
- handoff must update durable state atomically before the next writer starts;
- stale or ambiguous writer state fails closed.

Parallel writes to separate worktrees are a later feature and are not part of P6.5.

## Direct coding backend

DevSpace is the preferred candidate for the direct-workspace backend because it already provides:

- workspace identity;
- managed Git worktrees;
- project instruction loading;
- skills;
- file mutation and command tools;
- command sessions;
- Git-backed `show_changes` / review refs;
- Windows support.

ChatGPT should not need unrestricted raw shell/filesystem access outside the supervised workspace.

The preferred production architecture is to proxy the required DevSpace semantics through Supervisor Bridge so execution mode, write leases, event logging, and revision checks remain enforceable.

A direct second MCP connection from ChatGPT to DevSpace may be useful for experiments, but is not the target architecture because the Supervisor could not reliably enforce the single-writer invariant or audit every direct mutation.

## Codex backend

The Codex backend remains replaceable.

Candidate implementations:

- existing `codex-control-plane-mcp` adapter;
- Local-Codex-Bridge adapter;
- future enhanced DevSpace Codex runtime.

The Supervisor Core consumes backend-neutral operations:

```text
start_plan
start_execution
observe
steer
interrupt
list_pending_interactions
respond_interaction
resume
```

The current Local-Codex-Bridge implementation is particularly useful as a reference/backend for live `turn/steer`, `turn/interrupt`, bounded observation, approval/user-input forwarding, and UNKNOWN-outcome handling for timed-out mutating acknowledgements.

## Handoff: ChatGPT -> Codex

A handoff must not be a blind provider switch.

Before Codex starts:

1. capture current task revision;
2. capture Git HEAD and direct-change review reference;
3. record current active decisions / HARD constraints;
4. capture validation status;
5. release ChatGPT write lease;
6. acquire Codex write lease;
7. build a bounded handoff Context Pack;
8. use read-only Plan Mode first when the task requires a new/changed plan;
9. keep the existing Supervisor Plan Gate before workspace-write execution.

Codex must receive the current effective goal, constraints, approved decisions, relevant direct changes, validation state, and exact next delegated objective rather than the entire ChatGPT transcript.

## Handback: Codex -> ChatGPT

When Codex completes, is interrupted, or reaches a supervisor gate:

1. collect the latest structured checkpoint;
2. capture files changed / diff review reference / validation;
3. release the Codex write lease;
4. optionally acquire the ChatGPT write lease;
5. refresh Context Pack;
6. let ChatGPT inspect, continue directly, steer/redelegate, or request a hard replan.

## Checkpoints across both writers

P5 checkpoint semantics become writer-neutral.

A checkpoint may be sourced from:

- Codex runtime events;
- DevSpace `show_changes` / command validation;
- Git diff / HEAD changes;
- user override;
- explicit handoff/handback.

The normalized checkpoint model remains:

```text
HEARTBEAT | PROGRESS | GATE
completed
in_progress
files_changed
validation
assumptions
deviations
blockers
risks
next_steps
```

Raw provider event formats must not leak into Supervisor Core.

## Hard replan behavior

P6 hard replan applies to all modes.

If `active_writer=CODEX`:

- interrupt Codex;
- confirm/resolve interrupt state;
- capture work snapshot;
- classify partial work KEEP / MODIFY / DROP;
- supersede old plan;
- replan.

If `active_writer=CHATGPT`:

- stop further direct mutation;
- capture Git/review/validation snapshot;
- classify partial work KEEP / MODIFY / DROP;
- supersede old plan when necessary;
- replan or resume direct implementation.

The user intent and task identity remain canonical regardless of which writer produced the partial code.

## New events

P6.5 should add at least:

```text
EXECUTION_MODE_CHANGED
WRITE_LEASE_ACQUIRED
WRITE_LEASE_RELEASED
DIRECT_SESSION_STARTED
DIRECT_CHANGE_RECORDED
DIRECT_COMMAND_RECORDED
EXECUTION_HANDOFF

```

## Acceptance gates

P6.5 is complete only when tests demonstrate:

1. `DIRECT` task can edit through a fake DevSpace backend and persist/recover mode + workspace identity.
2. `DIRECT` cannot start Codex mutation without an explicit handoff.
3. `HYBRID` can hand off the same task/worktree from ChatGPT to Codex and back.
4. ChatGPT and Codex cannot hold the write lease simultaneously.
5. stale-revision handoff is rejected before the second writer starts.
6. Context Pack contains execution mode, active writer, latest direct review reference, and latest Codex checkpoint when applicable.
7. hard replan works while either ChatGPT or Codex owns the writer lease.
8. restarting Supervisor Bridge does not lose mode, lease, workspace binding, or task identity.
9. provider-specific raw event payloads are normalized before P5 checkpoint review.
10. the same Supervisor task can run under either Backend Profile A (Kandev + Control Plane) or Profile B (DevSpace + Local-Codex-Bridge) without changing task-memory semantics.
