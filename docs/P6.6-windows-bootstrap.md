# P6.6 — Windows Integration / Bootstrap / Real A-B Proof

## Scope

P6.6 turns the backend-neutral P6.5 architecture into a low-learning-cost
Windows startup path. It does not redesign Supervisor Core and it does not
implement the P7 delivery orchestration lifecycle.

The normal path is:

```text
install -> select project -> connect ChatGPT -> describe the task
```

Infrastructure names, ports, process IDs, SQLite paths, MCP transport details,
and provider credentials are advanced diagnostics only.

## Current code contracts

- `bootstrap.paths.AppDataPaths` owns persistent application locations. Windows
  defaults to `%LOCALAPPDATA%\\CodexSupervisorBridge` with `data`, `logs`,
  `runtime`, `config`, and `cache` children.
- Doctor checks for a compatible Bash shell because the current workspace
  provider does not use Windows PowerShell or cmd as its execution shell.
- `bootstrap.configuration.ConfigStore` persists versioned JSON settings with
  safe defaults and forward migration. Basic settings contain user intent;
  Advanced settings contain implementation details.
- `bootstrap.doctor.Doctor` returns `DoctorStatus` and `ComponentHealth` models.
  `user_view()` omits backend/provider diagnostics; `advanced_view()` includes
  bounded technical details.
- `bootstrap.repair.RepairService` performs bounded repairs: directories,
  settings, loopback port allocation, generated local MCP config, and stale
  process state. Unsafe authorization remains a user action.
- `bootstrap.process.ProcessManager` owns provider-neutral start/stop/restart,
  log paths, PID state, stale PID/lock cleanup, graceful shutdown, hard-kill
  fallback, bounded restart counts, optional readiness probes with bounded
  startup timeout, and fail-closed handling for an ambiguous live PID.
- `bootstrap.auth.FirstAuthorizationFlow` opens a browser authorization URL and
  stores the returned credential only through `SecretStore`.
- `bootstrap.devspace.DevSpaceBootstrap` emits the released DevSpace 1.0.x
  flat `config.json` shape at the provider edge, allocates its local port,
  creates the upstream `auth.json` contract under the same Bridge-managed
  directory, and launches `devspace serve` with a scoped
  `DEVSPACE_CONFIG_DIR`. It removes stale generated `config.jsonc` prototypes
  so the managed directory has one effective configuration source.
- `bootstrap.devspace_auth.DevSpaceLocalOAuthDriver` uses the MCP Python SDK
  OAuth client for protected-resource discovery, dynamic registration, PKCE,
  bearer injection, token persistence, and refresh. DevSpace's owner-password
  form is submitted only to the loopback authorization endpoint. OAuth tokens
  and the generated owner credential use `SecretStore` (Windows DPAPI by
  default); command/process diagnostics do not receive the credential. A fake
  loopback OAuth server drives the full protocol path in CI: 401 challenge,
  PRM/ASM discovery, dynamic registration, owner approval, token exchange, and
  restart reuse of persisted tokens without repeating authorization.
- `publicBaseUrl` remains null for Profile B. DevSpace derives its local
  origin from loopback host/port. ChatGPT attaches only to the Supervisor's
  separately authenticated HTTPS endpoint; DevSpace is never the public MCP.
- `bootstrap.remote.SecureRemoteAccessValidator` rejects non-loopback local
  binds, non-HTTPS public URLs, missing authentication references, and missing
  session identity before tunnel startup.
- `bootstrap.command_auth` enforces `ALLOW` / `ASK` / `DENY`, project-bound
  working directories, current revision, writer lease, dangerous-command
  blocking, bounded command sessions, and reconciliation latches.
- Direct Workspace now exposes only semantic `run_direct_workspace_command`
  and `poll_direct_workspace_command` tools. They use the existing durable
  two-phase operation fence, default to `ASK`, preserve long-running session
  state, and record bounded Git/review evidence after completion. The command
  session identity and lifecycle are also persisted in `direct_command_sessions`
  so a restarted Supervisor can resume a RUNNING provider session; polling or
  startup without a resumable identity fails closed into reconciliation.
- Process startup refuses an ambiguous live PID and the MCP HTTP entrypoint
  refuses non-loopback binds. Remote access must pass the HTTPS/auth/session
  identity gate instead of exposing the local server directly.
- Bootstrap `user_view()` projects internal repair operation names into
  user-level actions while retaining the detailed operation/provider data only
  in advanced diagnostics.
- `bootstrap.harness.ProfileABHarness` compares normalized Supervisor traces,
  not provider payloads or provider-native IDs.
- `BootstrapService` maps Doctor capability health into the existing
  `CapabilityResolver`, so Automatic selects the healthiest available backend
  profile without making backend choice a Basic setting.
- When an advanced Local-Codex-Bridge launch command is configured,
  `codex-supervisor start` routes it through the dedicated protocol bootstrap;
  it never invents a launch command when the user has not configured one.
- Local-Codex-Bridge 2.1.3 requires Node.js 24+. Its canonical stdio launch is
  `node <repository>/dist/src/index.js`; bootstrap rejects `npm start` because
  npm lifecycle output can corrupt strict JSON-RPC stdout. `CODEX_EXE` remains
  optional when `codex` is already on `PATH`.
- Advanced `local_codex_repository` plus `executable_paths.node` lets Doctor
  and `codex-supervisor start` resolve the canonical Node entrypoint
  automatically, and Doctor runs `node --version` to enforce the upstream
  Node.js 24+ requirement. An explicit `process_commands.local_codex_bridge`
  remains the override; any npm-family launcher (`npm`, `npm.cmd`, `npm.exe`)
  is rejected at the MCP stdio boundary.

## Upstream compatibility

Checked on 2026-08-28:

- npm `@waishnav/devspace` latest is `1.0.8`; its released user configuration
  contract is flat `config.json` plus `auth.json`, with Node `>=22.19 <27`.
- GitHub `main` contains a newer pre-release layout that promotes the old flat
  file to versioned nested `config.jsonc`. Bridge does not generate that
  layout yet. Doctor records tested versions `1.0.5` and `1.0.8`, supports
  `>=1.0.5,<1.1`, and marks an incompatible installed release as needing a
  compatible local-workspace repair.
- `zoeynine/Local-Codex-Bridge` 2.1.3 exposes the required semantic tools
  (`codex_turn`, `codex_observe`, `codex_steer`, `codex_respond`,
  `codex_interrupt`) and documents the direct Node build entrypoint used
  above. Its contract is frozen in `tests/fixtures/local-codex-bridge/`.

## Profile policy

Profile B (DevSpace + Local-Codex-Bridge) is preferred only when its capability
checks are healthy. Profile A (Kandev + codex-control-plane-mcp) remains the
fallback until the real Windows scenario passes. A running task must not change
worktree ownership implicitly during fallback selection.

## Local commands

```text
codex-supervisor configure --project D:\Projects\xxx [--style automatic] [--local-codex-repository D:\Local-Codex-Bridge] [--node C:\node.exe]
codex-supervisor doctor
codex-supervisor status
codex-supervisor repair
codex-supervisor start
```

Use `--json --advanced` for future GUI/diagnostic consumers. The generated MCP
configuration contains only the loopback Supervisor endpoint; credentials are
never written to it. `configure` persists the project directory and Basic user
intent (development style, command policy, delegation, auto commit/PR) into
the versioned settings file.

## Real-machine boundary

The current implementation is covered by portable unit tests, fake process
tests, protocol tests, and the Windows GitHub Actions job. It does not claim
real Windows installation, DevSpace first OAuth authorization, Codex account
readiness, ChatGPT Web Remote MCP attachment, tunnel-provider login, or the
full Profile A/B live scenario. Those gates require an opt-in Windows machine
and user authorization after the code-level work is complete.
